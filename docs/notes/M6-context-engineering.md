# M6：上下文工程

日期：2026-09-22 · 对应里程碑 M6（上下文工程）

M6 之前，agent 每次请求都把完整历史发出去，从不关心还剩多少地方。对话短的时候没事；
让它读十几个文件、或者 daemon 一轮里连调几十次工具，历史迟早超过窗口：服务端直接回 400
（Ollama 更糟，悄悄截断），这一轮报错结束，下一轮照样超长，会话就卡死了。

这一篇记的是：怎么知道还剩多少地方、快满时按什么顺序腾地方、腾地方和前缀缓存怎么打架，
以及五次真实模型实测里踩到的坑——这一节的大部分设计是被实测改出来的。

| 文件 | 管什么 |
|---|---|
| `agent/context.py` | 纯函数：估算、预算、校准系数、清理挑哪些、压缩切在哪、压缩指令、超长报错识别 |
| `agent/loop.py` | 每次请求前按预算清理 / 压缩；`Agent.compact()`；超长兜底；中断修复跟着下标走 |
| `agent/session.py` | `replace` / `compact` 两种新记录；上次实际用量和校准系数（只在内存里） |
| `spaces/store.py` | 工作台的「模型看到的历史」`sessions/model/<sid>.jsonl`，从展示用的 jsonl 迁移 |

## 1. 预算：上次的实际用量 + 之后的估算

要腾地方，先得回答「下一次请求大概会发多少 token」。三种办法各有毛病：

| 办法 | 问题 |
|---|---|
| tiktoken 精确计数 | 多一个依赖；只对 OpenAI 的模型准，DeepSeek / GLM / Qwen 的 tokenizer 各不相同 |
| 只看上次的 `usage` | 看不到上次请求之后新来的东西——刚回来一个 3 万字符的工具结果、下一次请求还没发，恰恰最危险 |
| 纯按字符估 | 误差随会话变长越积越大 |

所以两者叠起来：上次请求返回的 `prompt_tokens` 精确覆盖了那次发出去的 system + 工具 + `messages[:n]`，
之后新增的消息按字符估（ASCII 3 个字符一个 token、非 ASCII 一个字一个、每条消息加 4）。
估算误差只出在两次请求之间新增的那一小段，每请求一次就校准一次。估之前先过 `prepare_messages`：
不回传的思考内容不算。

字符规则故意往大了取，实测 DeepSeek 上高估 20%～30%（`/context` 最后一行会显示「校准：上次请求实际
X，同一段按字符估 Y」）。平时没关系，高估只是早一点动手；但**清理和压缩会让「上次的实际用量」作废**
（它覆盖的历史变了），这时只剩全量估算，偏高 25% 就开始误事——见第 7 节的坑 5。所以又加了一个
**校准系数** = 实际用量 ÷ 同一段的字符估算，每次请求更新，不随历史改动作废；没有实际用量可用时，
全量估算乘上它。系数限制在 0.5～2，换了模型就不用。

输入上限 = `context_window` − 给输出留的余量（`max_tokens`，没配就取 16k 和窗口 1/4 中较小的）。
下文说的百分比都相对这个上限。

## 2. 三级策略

| | 写入时截断（M2） | 清理旧工具结果 | 摘要压缩 |
|---|---|---|---|
| 触发 | 单个结果超 3 万字符 / 500 行 | 占用 ≥ `clear_at`（60%） | 按清完的样子算仍 ≥ `compact_at`（80%） |
| 怎么做 | 只留开头，完整内容落盘 | 较早的 tool 结果换成占位符，原文落盘 | 调 LLM 把早期对话写成摘要 |
| 成本 | 零 | 零 | 多一次请求 |
| 确定性 | 确定 | 确定（占位符一字不差） | 不确定（每次摘要都不一样） |
| 缓存影响 | 不影响（写进历史时就定了） | 从第一条被改的消息起失效 | 之后整段前缀失效 |
| 能不能找回 | `read_file` 读落盘文件 | `read_file` 读落盘文件 | 找不回（原文只在会话文件里） |

**清理**只动 tool 消息的 content：消息本身和 `tool_call_id` 都在，配对不断；调用了什么、参数是什么
也都在 assistant 消息里，模型知道自己做过什么。不清的：最近 `keep_tool_results` 个、模型还没看过的
（最后一条 assistant 之后的——一次并行 5 个调用时，只按「最近 3 个」算的话，前两个模型一眼没看就没了）、
已清过的、短于 300 字符的、模型把清理文件读回来的。原文落盘而不是让模型重跑：`bash`、MCP 工具重跑
可能有副作用，或者结果已经变了。

**压缩**的切点只落在两种位置：user 消息（轮次边界），或紧跟工具结果的 assistant 消息（一轮内部的
步骤边界，daemon 一轮几十步也能压）。永远不落在 tool 上，所以 tool_calls 和结果要么一起压掉、要么
一起留下；切点前一条也不能是 user，追加压缩指令时才不会两条 user 挨着。保留最近约 1/4 的原文。
摘要用 user 消息放在开头（`[对话摘要] …`），保留部分以 user 开头时再补一条固定的 assistant 回复，
照顾严格要求一问一答交替的服务。摘要不塞进 system prompt：那样连工具定义在内的整个前缀都失效。

压缩指令让模型保留：用户的目标和原话要求、已完成的事和结论、文件路径 / 函数名 / 报错原文、
没做完的事和下一步。「该留什么」要理解内容才判断得了，所以这一步只能交给 LLM；什么时候压、
压哪段、摘要放哪，全是 Python 规则。

## 3. 最重要的取舍：腾地方 vs 前缀缓存

前缀缓存按**字节前缀**匹配：这次请求的开头和之前某次请求一字不差的部分才算命中，价格便宜一个量级，
首字也更快。M6 的每个动作都在改历史，所以处处要和缓存打交道：

- **system prompt 和工具列表整个会话不变**：只精确到日期，MCP 工具在第一次请求前注册完。
  有回归测试守着——一个会话里所有请求（含摘要请求、跨轮、清理和压缩之后）的这两样都相同。
- **清理一次清完**：清理改的是历史中间，缓存从第一条被改的消息起全部失效。每次请求清一点，就每次都
  打破一次缓存，比不清还贵。所以过了阈值就把能清的一次清完——落到阈值以下很远，要再涨一大段才会
  再触发，中间很长一段前缀是稳定的。能省下的不到输入上限的 5% 就不清，留给压缩。
- **落盘文件名只由内容决定**：同样的结果每次生成一样的占位符。工作台早期每轮都要重新清一遍，
  靠的就是这个。
- **摘要请求复用上一次请求的前缀**：`[system, *messages[:切点], user(压缩指令)]`，tools 照带。
  `messages[:切点]` 正好是上一次请求的前缀，要付全价的只有指令和摘要输出。另起一个「总结专用」
  的 system prompt、把旧消息拼成文本发过去看着干净，但全部输入都是缓存未命中。

这个设计第一次实测只命中了 30%～45%，后来又发现两处破坏前缀的地方：

**思考内容的回传规则**。DeepSeek 的 profile 是 `reasoning_echo = "current_turn"`：最后一条 user
之后的 assistant 才回传思考内容。压缩指令也是一条 user，追加上去后，本轮的思考内容被当成
「上一轮的」去掉，前缀在本轮第一条带思考的消息处就变了。用 trace 重放做实验：同一个前缀，
去掉思考内容 58% 命中，保留 99% 命中，DeepSeek 接受上一轮的思考内容、不报错。

于是 `LLM.stream()` 加了 `continue_turn`：最后一条 user 不算新的一轮。但它不能恒为 True——
要看**上一次请求里思考内容从哪条 user 之后开始回传**：那条 user 在切点之前（一轮中途压缩、
新一轮一开口就压缩）就接着回传；在切点之后（`/compact` 只留最后一轮，压的全是更早的轮次），
上一次请求里这些思考内容本来就去掉了，也得去掉。第一版恒为 True，实测里就撞上了后一种情况。

**先清理后压缩**。清理和压缩在同一次请求前都触发时，清理先改掉了前缀，摘要请求就吃不到那部分
缓存——而被清的结果反正也要压进摘要，等于白清。改成：判断要不要压缩时按清完的样子算，要压缩就
先在原历史上压，再看保留下来的部分要不要清。

改完之后实测，摘要请求命中 95%～97%，前缀和上一次请求一字不差。

**没改的一处**：普通的换轮也有同样的问题——用户每发一条新消息，上一轮的思考内容就被去掉，上一轮的
内容全部未命中。改成 `reasoning_echo = "all"` 能全部命中，代价是思考内容永久留在上下文里，
更早触发清理和压缩。这是 profile 里的开关，留给 M9 用评测对比。

## 4. 入口：自动、手动、兜底

- **自动**：每次请求前都查，不只在每轮开始时。
- **`/compact [重点]`**：重点追加进压缩指令；切在最后一条 user 上，完整保留最后一轮。
- **超长兜底**：服务端回 400 / 413 且报错里有上下文超长的说法（各家说法不一，按关键字认），
  还没有任何输出时，强制压缩一次、只留最后一步，重试这一步；每步只兜底一次。只留最后一步是因为
  估算已经被服务端证明不可信，按它留 1/4 的话留下的可能还是超长。
- **Ollama**：超过 `num_ctx` 是悄悄截断而不是报错，本地 profile 只能靠预算，`context_window`
  要和 `num_ctx` 一致。

## 5. 工作台的两份历史

工作台以前每次输入都从展示用的 jsonl 重建历史，而那份是按事件镜像的：清理、压缩、中断修复都
不产生消息事件，所以全存不下来——压缩每轮要重新调一次 LLM；中断正在执行的工具后留下没有结果的
tool_call，下一条输入会被 API 拒绝（这是个一直潜伏的 bug）。

现在分成两份：`sessions/<sid>.jsonl` 给界面显示实际发生过什么，工具结果是原文；
`sessions/model/<sid>.jsonl` 是 `SessionStore` 的操作记录，模型看到的历史，和 REPL 走同一套
Session 方法。老会话第一次用到时从展示用的那份迁移，顺手补上悬空的 tool_call。

放弃的做法：把修复后的历史同步回展示用的 jsonl——界面会显示占位符和摘要，而压缩改写整段前缀，
一行一条消息的 jsonl 根本没法表示。Runner 把 Session 留在内存里——重启就没了。

## 6. 真实模型实测（deepseek-flash）

为了触发清理和压缩，有几次在内存里把窗口缩到 16k（输入上限 12k），读 4 个各占上限 1/3 的源码文件——
这是故意放不下的任务。

| 实测 | 结果 |
|---|---|
| `/context` 校准 | 字符估算高估 29%～31%（带 20 个工具）、20%～25%（7 个工具）；工具列表是前缀里最大的一块 |
| 清理，无读回保护 | 模型读回清理文件 → 又被清 → 再读回，一轮转了 8 圈，21 次请求 |
| 加读回保护后 | 读回 3 个文件后作答，10 次请求；上下文涨到假窗口的 133%，只能交给压缩 |
| 压缩，第一版 | 5 次滚动压缩，任务完成，26 次请求；摘要请求命中只有固定前缀（约 2k） |
| `/compact`，第一版 | 压了 17 条，压缩后凭记忆答对了读过的文件和规则；摘要请求命中 58% |
| 回放实验 | 同一前缀：去掉思考内容 58%（真实请求），保留思考内容 99% |
| 修好之后 | 小窗口 4 次压缩命中 95%～97%；`/compact` 命中 97%，前缀一字不差；提示行和 `/context` 数字一致 |

## 7. 踩到的坑

1. **清理和读回来回拉锯**。清掉的结果模型要用，读回来又被清。修法：模型读回来的清理文件不再清——
   它主动读回，说明确实需要，这时该交给压缩。但后来发现模型也会**直接重读原文件**，绕过这条保护。
   没再加规则：「结果被清后又发起一模一样的调用」也保护的话，写代码时改完文件再重读这种正常操作
   也清不掉了。根本原因是任务同时需要的内容超出了窗口，这时任何策略都只能折腾或者靠摘要。
2. **`/compact` 只留了最后一步**。按「最后一个合法边界」切，这一轮调过工具的话只剩最后那条回答，
   问题本身被压进了摘要，摘要里写着「尚未作答」、后面紧跟着答案。单元测试没发现，因为测试对话里
   没有工具调用。改成切在最后一条 user 上。
3. **思考内容回传让摘要请求吃不到缓存**，以及修的时候第一版把 `continue_turn` 写死成 True，
   反方向又错了一次。见第 3 节。
4. **先清后压白清一次**。见第 3 节。
5. **估算口径不一致**。清理 / 压缩后提示行写 3,023，紧接着 `/context` 显示 6,043：提示行用
   「压缩前（基于实际用量，基本准）− 压掉部分的字符估算（偏高 25%）」，从准数里减掉偏大的估算，
   删得越多越偏小；`/context` 只剩全量估算，偏高。要紧的是决策：清理之后判断要不要压缩用的正是
   偏高的全量估算，可能白压一次。靠校准系数统一了口径。
6. **滚动摘要越滚越长**。1,544 → 1,887 → 2,519 → 3,104 → 4,160 字符，每压一次都在旧摘要上加码。
   指令里加了「合并后整体仍不超过这个长度，越早的内容越概括」，之后不再一路变长，但在很紧的上限
   （1200 字）下仍会写到两倍左右；正常窗口（3000 字）下守住了。没用 `max_tokens` 硬截断：
   思考 token 会不会算进去不确定，万一思考就把额度用完，摘要会被截断甚至为空。
7. **测试里按文字认摘要请求会误判**：读的文件正是 `context.py` 时，工具结果里就有压缩指令那句话。
   只认 user 消息。
8. **改坏验证抓到了两个不够强的测试**：「清理跨输入保留」在旧代码上也能过（旧代码每轮重新清、
   占位符又是确定的），改成断言「第二条输入没有再清一次」；「最少收益」的测试离阈值只差 2 token，
   稍改措辞就会翻车，换了更稳的数。

## 8. 现在的缺口

- `[context]` 是全局配置。比例相对各 profile 的输入上限，大体通用；但 `keep_tool_results` 是个数，
  32k 的本地窗口里 3 个满额结果就能占满，以后可能要按 profile 覆盖。
- 摘要长度只靠指令约束，在紧的上限下会超。
- 重复读取原文件的保护没做（第 7 节坑 1），留给 M9 用真实长任务评测。
- `reasoning_echo = "current_turn"` vs `"all"` 的缓存 / 上下文权衡没测（第 3 节）。
- 工作台还没有手动压缩的入口，`context_edited` 帧界面也还没显示。
- 摘要是记不住跨会话的东西的：会话结束就没了。真正要长期留下的信息（用户偏好、项目约定）
  归 M7 的记忆，压缩只管这一个会话里腾地方。
